# 更正本期已经入账的普通凭证

收到正式做账委托后，在绑定的账套和期间内自行核实、执行更正和读回账表。先判断是记账错误、已解释的清算时差，还是原件尚有歧义。交付列出实际改动、保留事项及其原因。仅做复算、情景或报表时，调整单列在底稿。

## 现场准备

生成正式宿主时一次指定 `--voucher-corrections delegated --source-root <客户原件目录>`，随后按原有流程绑定账套及期间。宿主会固定原件版本。默认选取该目录直接包含的受支持文件，现场混放客户原件和旧取数表时，以可重复的 `--correction-original <原件绝对路径>` 明确选择，子目录的原始文件也可这样选择。客户不需要按凭证逐张授权。原件实质变化时在新授权工作区选取新版本，并接回原账套、记忆和交接目录。旧现场升级时在原件选择完成后生成新工作区。原有期间控制继续生效。

## 从分录回到原件

1. 从银行结单、回单、原始凭证和账簿分别取值，定位错在哪个字段及其对方。流水的金额和余额两栏可互相检验；OCR 两次结果冲突时回读原图字段。有多笔收款合并入账时，保留每一笔及其客户。核实应收、预收等科目和真实对方。扣款日与税款入库日有不同业务意义，先核完税凭据。
2. 从已绑定账套同期间的 `finance_query` 节点 `voucher.generated.list`（`params.view="index"`）取得真实 `voucherId`，用 `voucher.detail` 的 `params.view="check"` 核分录及原件线索。对确需更正的凭证，调用 `voucher_correct`，传 `action:"inspect"`、`accountSetId`、`period`、`voucherId`。使用返回的 `fingerprint`。从本工作区的 `.finance/correction-sources.json` 取宿主已固定的原件路径和 SHA-256，与实际读取的原件对应。历史人工凭证和系统派生凭证应根据各自依据及已有更正流程处理。
3. 用同一个 `voucherId` 提交 `action:"apply"`，带上 `expectedFingerprint`、唯一 `operationId`、完整新分录 `entries`、`voucher_date`、`summary`、原件映射 `businessEvidence` 和独立复核 `proof`。复用 `voucher_create` 的正式入账字段映射。检查对象已变时重新读账；同一次调用中断则先按原操作号、原参数查询或重试。
4. 成功后按回执核对凭证号和更正后指纹。使用 `finance_query` 查银行科目及受影响的客户、供应商明细，按科目传 `nodeId="ledger.general"`、`accountSetId`、`period` 和 `params.code`；重出受影响的底稿、报表及税费测算。回执或账簿结果缺失时保留未完成状态。无需另外执行反过账、删除或重新编号。

## 独立复核凭据

在 `businessEvidence.mappings` 中使用 `transform="identity"` 时，每条 `sources` 只填一处直接给出该字段原值的来源。金额映射到金额单元格，日期映射到日期字段。对方名称、业务号等核对依据放在对应的字段映射或 `proof` 中。确由多笔金额合计的分录按实际加总关系使用 `sum`。

`proof.kind="bank_statement"` 适用于人民币普通收付款。传委托中固定的原件绝对 `path`、`sha256`、每笔流水位置和对应的银行及往来科目。支持多笔同日合并入账。工具独立比较日期、收付方向、金额、对方及前后余额，并核对完整的银行与往来分录。合法清算时差保持原状。一个合成 CSV 示例为：

```json
{
  "kind": "bank_statement",
  "path": "D:/合成原件/流水.csv",
  "sha256": "<现场读取的64位摘要>",
  "columns": {"date":"日期","party":"对方户名","inflow":"收入","outflow":"支出","balance":"余额","priorBalance":"上笔余额"},
  "lines": [{"row":4,"bankCode":"100201","counterCode":"112201"}]
}
```

表头默认第 1 行；XLSX 另传 `sheet`。若无上笔余额列，工具在正序或倒序结单的相邻行核对前余额与收付差，第一笔交易需要可核的期初余额。工作簿支持文本日期和带日期格式的 Excel 整数日期。以序号保存日期的工作簿，还需要为正式入账字段提供可核的标准日期映射。对方户名应与往来明细科目匹配。只支持有明确来源和分配依据的行。

Windows 上的 PNG/JPG 结单可提交每一行的 `cells` 代替 `columns`，其中 `date`、`party`、`amount`、`priorBalance`、`balance` 均为原图像素矩形 `[x,y,width,height]`。本机 Windows OCR 在固定的原图上独立识别这些字段，其中前余额取上一行。原件不经模型传输。OCR 无法辨清或日期、余额、金额、往来不一致时，重新定位或使用另一份经授权的银行原始导出；其余已核业务继续。扫描件的日期和金额仍需在 `businessEvidence` 中按支持的格式映射，OCR 校验独立于派生表执行。

其他普通非银行凭证可用 `proof.kind="document"` 提交原始结构化记账支持资料的 `path` 和 `sha256`。日期、每一条借贷金额与科目编码均须由 `businessEvidence` 直接映射到同一份原件；分录须能追溯原凭证已有的原件记录。金额变更、科目重分类和确认期间各以能证明其语义的资料为依据。

非银行支持表可以是客户原有的报销分录、应付登记等 CSV、XLSX 或 JSON。表格的第 1 行给出字段名称。每行一条分录时，可用 `凭证日期、摘要、科目编码、借方金额、贷方金额`，同一笔业务的日期逐行填写。每行同时登记借贷双方时，可用 `凭证日期、摘要、借方科目编码、借方金额、贷方科目编码、贷方金额`。在 `businessEvidence` 中将每个发生额指向原件中相应方向的金额列，同一原件单元格只能计入一次。税额、费用、往来等原凭证已引用的业务行均要覆盖。

业务系统 JSON 导出也支持每张凭证头有 `date`、`summary`，其 `entries` 数组中每条分录有 `code`、`debit`、`credit`。例如 `/0/date` 可以和 `/0/entries/0/debit` 一起取用，凭证头日期须能追溯到原凭证已经引用的同一记录。改写摘要时从相应业务行或凭证头取原文。只有总金额、缺少借贷含义的清单，可用于核对金额，需从原有可核实的记账支持资料补足方向后再执行更正。
