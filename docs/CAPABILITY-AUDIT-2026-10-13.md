## 结论

已经完成了“本机 Codex → finance MCP → 本地记账后端 → SQLite”的基础链路，具备可运行的记账、报表、标准格式旧账导入 MVP。原站五个业务域中，智能核算与导入旧账已有部分实现，智能开票、全税种申报、个税申报仍需开发。

当前还不能按“原网站已完整复刻”理解：逆向归档揭示了前端工具契约与业务入口，未取得其服务端业务引擎和 Skill 正文；本地是独立实现。原站功能范围以下述归档为依据，本次未登录原站重新验收：

## 1. 已实现到什么程度

这里区分“后端已有实现”和“Codex 可以通过已公布 MCP 工具直接调用”。Codex 另行执行脚本访问 REST 是可行的集成方式，但不能据此把未注册工具视为已经接好。

| 功能 | 本地实现 | 当前 Codex MCP 接入 | 尚缺内容 / 限制 |
|---|---|---|---|
| 账套管理 | 新建、查询、删除，自动载入标准科目 | 查询可用；新建可通过旧账导入创建；独立新建/修改/删除工具未齐 | 企业信息同步、完整账套维护、稳定的当前账套上下文 |
| 科目、期初余额 | 查询、新增科目、录入期初 | 科目查询可用；独立维护工具未齐 | 科目层级与报表汇总、期初校验及锁定、多准则完整映射 |
| 凭证 | 多分录、借贷校验、草稿、过账、反过账、删除 | 创建、校验、查询可用 | 凭证修改/审批链；反过账、删除等独立 MCP 入口；封账约束 |
| 财务报表 | 试算平衡、资产负债表、利润表、现金流量表、按科目查账 | 三大报表可查；期末状态中包含试算；明细账专用查询未接齐 | 明细科目归集、完整准则适配、复杂现金流分类、正式导出 |
| 结转损益 | 月度结转、年末利润结转逻辑与测试已有 | `carry_forward_profit` 未出现在 MCP 工具清单 | 注册工具、零利润与撤销/重算等边界 |
| 固定资产 / 无形资产 | 资产卡片、直线法折旧/摊销、同期防重复 | `asset_list`、`asset_create`、`depreciation_run` 未注册 | 接入 MCP；资产购入凭证与卡片勾稽、处置、撤销重计提 |
| 期间管理 | 已有期间的结账/反结账、结账后禁止新增凭证 | 无专用 MCP 变更工具 | 新期间登记缺陷、完整封账和结账前检查 |
| 旧账导入 | JSON / 四张 CSV；UTF-8、GBK；预检；事务导入 | `legacy_book_import` 可用，支持本机 `paths`，默认预检 | 任意 Excel 的自动理解、列映射、金蝶/用友专用适配、重复导入识别 |
| Excel 转 CSV | 有 `xlsx-to-csv.py` 脚本 | 可作为前处理步骤，非 MCP 原生 Excel 导入 | 脚本主要摊平工作表、匹配表名，不解决任意账表结构；`.xls` 需另行转换；本次未执行转换脚本 |
| 打印 | 页面已有 `window.print()` | 无专用文件输出工具 | Excel 导出、规范分页的 PDF、凭证打印模板 |
| 业务规则 / 智能体 | 五个业务域名称、21 份 Markdown 文件可读取 | `skills_list` / `skills_read` 可用 | 文件仍含模板和 TODO；旧账 Skill 新增了逆向说明，但执行工作流仍待补全；未见完整五智能体调度实现 |

主要实现位置：`06-workbench/server/accounting.mjs`、`06-workbench/server/server.mjs`、`06-workbench/public/app.js`。

另有以下占位行为：

- `invoice_collect`、`invoice_file`、开票预检/编码/开票/红冲相关工具：未实现。
- `declaration_query`、`tax_declaration_query`：未实现；尚没有实际申报提交链路。
- finance MCP 中的 `exec`：后端没有执行分支，返回未实现。它与 Codex 自身的命令执行工具不是同一个实现。
- `finance_task_status`：固定回复 `completed`，没有按任务 ID 查询真实任务状态。
- `update_plan`：返回 `saved: true`，当前分支只回显入参，没有持久化。
- 上下文工具只返回账套列表及指定账套的期间，未保存“当前选中账套”；`finance_query` 后端实际要求提供账套 ID，与 schema 中的“可缺省”描述不一致。

证据位置：`06-workbench/server/server.mjs:129`；`05-reconstruction/codex/mcp/finance-mcp/server.mjs:61`。

## 3. 还没有落地的完整业务域

| 业务域 | 需要建设的内容 | 对本机版的建议 |
|---|---|---|
| 银行流水 | 文件解析、交易标准化、去重、收付款匹配、流水入账、银行对账 | 优先做本地文件导入，再考虑银行通道 |
| 发票处理 | 图片/PDF/结构化文件解析、发票台账、重复识别、原件关联、生成凭证 | 先做本地票据到凭证，查验与采集另接数据源 |
| 智能开票 / 红冲 | 商品及抬头管理、编码匹配、预检、提交、回执、红冲状态 | 当前缺实际服务通道，需要独立接入 |
| 工资 / 个税 | 员工、工资表、工资凭证、个税计算、申报、缴款回执 | 先做工资核算，申报能力作为后续阶段 |
| 全税种申报 | 税种信息、取数、申报表、校验、提交、回执、更正撤销 | 先完成申报数据准备，再对接提交链路 |
| 辅助核算 | 客户、供应商、部门、项目、员工等维度及明细报表 | 对真实往来业务很重要，建议早于商业化功能 |
| 企业基础数据 | 银行账户、工商信息、人员、税务信息、税种核定 | 先支持本地维护，自动同步另做 |
| 数据保障 | 操作记录、备份恢复、附件证据链、导入批次追踪 | 本机长期使用也应建设 |
| 商业平台 | 多用户/租户/角色、微信登录、SSO、套餐计费、团队席位、企业微信渠道 | 本机阶段可以暂缓 |
| 网站交互外壳 | 原站专用会话界面、子智能体进度面板、附件上传、语音入口等 | 先使用已有 Codex 会话与工具接入；独立网站以后再做 |

## 4. 本次复现的可靠性缺口

以下均在独立临时数据库复现，不是只凭 README 推断；本次仅记录，尚未修复。

| 问题 | 最小复现与结果 | 建议验收目标 |
|---|---|---|
| 结账后仍能反过账 | 新建已过账凭证 → 结账 → `unpostVoucher`，成功变为草稿 | 封账期间所有影响账目的变更均被拦截，先显式反结账 |
| 手工期初没有平衡约束 | 只录入银行借方 100，无贷方，`setOpeningBalances` 接受 | 保存/启用阶段有明确完整性检查；批量失败不留下部分修改 |
| 零利润结转失败 | 收入 100、费用 100 → 结转，报“第3行金额不能为 0” | 收支相等仍能结转，且无零金额分录 |
| 银行明细科目漏报 | 新增 `100201`，借 100 / 贷资本 100 → 资产表资产 0、权益 100 | 支持父子科目归集，并确保试算、资产表、现金流取数一致 |
| 删除折旧凭证后不能重计提 | 计提 → 反过账 → 删除凭证 → 再计提，返回无需计提，原计提记录仍存在 | 撤销凭证与计提记录同步处理，账面折旧与资产卡片一致 |
| 新期间不能单独登记 | 已有 2026-01，调用 `setPeriodStatus(...,'2026-02','open')`，报 `period_not_found` | 页面“登记期间”可创建新期间，期间格式及顺序正确校验 |

对应代码位置：`accounting.mjs:67`、`:97`、`:203`、`:292`、`:475`、`:586`；页面登记入口 `public/app.js:458`。

此外，代码检查发现下列能力需要专项验收：

- 会计准则字段可填写不同准则，但建账仍加载同一份 COA；不能视作两套准则完整支持。
- 现金流量表按对方科目和金额比例分类，复杂混合分录、明细科目需验证；间接法末行直接取直接法经营净额，不是独立勾稽验证。
- 结转的年末独立执行、红字/负余额、补录后重算，以及跨期折旧尚需补充场景。
- 创建资产卡片不会自动生成资产购入凭证，需要补齐卡片与总账校验。
- Agent 导入默认仅预检；REST `/api/import/account-set` 省略 `dryRun` 时却会正式导入，文档与接口默认值需统一。
- 原有 MCP 冒烟测试的失败分支假定错误文本是 JSON，后端无法连接时可能出现二次解析错误，应单独修复。

## 6. 建议按什么顺序继续

### 第一阶段：让已有能力在 Codex 内完整、可靠地使用

1. 修复第 4 节六项缺陷，并为这些真实失败场景增加回归用例。
2. 注册资产、折旧、结转四个后端已有工具；补齐账套/科目/期初/凭证状态/期间/明细账必要工具。
3. 统一参数 schema、错误结构和上下文；目录标明“可用 / 未实现”，清理虚假的完成/保存反馈。
4. 补写 `bookkeeping` 与 `legacy-book-import` 的实际流程和业务规则，明确账套、期间、来源、校验、执行结果。
5. 做一条可以复验的对话流程：导入旧账 → 校验期初 → 录入业务 → 核对资产 → 折旧 → 结转 → 检查 → 结账 → 出报表；每步给出实际凭证或报表证据。

完成标准：常见操作无须临时写 HTTP 脚本，工具公布状态与实际能力一致，错误场景不会破坏账簿一致性。

### 第二阶段：形成有用的自动记账流程

1. 银行流水导入、去重、匹配和凭证草稿生成。
2. 发票与报销单解析、附件留存、单据和凭证关联。
3. 工资表入账、辅助核算、往来账查询。
4. 任意 Excel 导入的表头识别、列映射预览、格式适配和批次去重。
5. Excel/PDF 输出、备份恢复、关键操作记录。

完成标准：能够对一套经脱敏的真实企业月度资料走完“单据 → 凭证 → 核对 → 结账 → 报表”，且结果可追溯。

### 第三阶段：税务通道与网站产品化

先做税务取数与申报表校验，再接开票、查验、申报和回执通道。待本机流程稳定后，再按需要建设独立网站、账户权限、团队协作和商业化模块。

当前最值得先做的是第一阶段；继续大量提取原站界面，不能替代本地业务实现、规则与可靠性验证。
